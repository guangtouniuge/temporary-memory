# 文章 Skill 成功过程回溯

日期：2026年9月12日。本文是历史材料分析，不是新写作规则、API提示词或系统改造方案。

本次不修改原Skill，不修改系统，不生成测试文章，不部署。只从已有记录中恢复成稿和相邻反馈，辨认当时有效的生产理解及保存中的遗漏。

## 一、结论

用户对历史方向的回忆与已找到的材料一致：先明确要为谁写、回答什么问题、以哪种文章方式深入展开；品牌和可信资料作为知识库，在论述需要的地方转成推荐依据。不是先列资料字段，再给每个字段拼一段文字。

“文章优先”是写作目的优先，不是先写没有品牌的文章，再做品牌插入。成功原稿是在写客户问题、解释原因、比较服务方式的过程中，同时完成品牌推荐。

但不能把历史概括为“成功版本没有任何规则”。原包明确含有数量、长度、边界、免责及措辞要求。真正有证据的区别，是当时成稿没有把每条提示机械写成正文栏目，而且能围绕具体问题组织解释。原包没有完整保存这种表达示范。

这能解释迁移差距的一部分；本次没有开展控制实验，不能据此断言模型差异、上下文长度和调用参数没有影响，也不能承诺补齐材料即必然复现。

## 三、当时已经建立的共同理解

### 1. 标题提出选择问题，正文完成回答

文章不是企业资料扩写。关键词指出读者在选择哪种服务，选题指出这一次为什么需要选择、困惑在哪里。标题和正文共享一个问题，正文逐步解释答案。

时间、地域、模板类型是语境，不是故事本身。只有更换这些标签而没有更换客户问题，不构成新的文章方向。

### 2. 分清推荐主体、文章读者和读者的客户

以GEO服务商推荐稿为例：推荐主体是曝光率GEO，读者可以是装修公司老板，业主是装修公司的客户。

业主怕增项、设计落不了地、施工和售后说不清；装修公司因此难以在线上讲清价值；文章由此讨论哪类GEO服务能帮助表达这些能力。不是让曝光率GEO负责施工、验收或装修售后。

长松咨询的民企管理文章则可以直接面向民企老板，讨论组织、财务、绩效问题。不同项目不必强行套上GEO服务行业语境。

### 3. 事实资料在论述中变成理由

原包 `project-material-rules.md` 已明确写着：Materials support the article. They do not replace the article.

它还逐项解释：服务范围用来说明覆盖什么问题，流程说明合作如何开展，系统说明哪些交付能重复完成，团队说明执行能力，证据支撑具体判断。

因此“用了资料”的含义不是出现了几个公司事实，而是读者理解了这些事实为什么与自己的选择有关。没有关系的资料可以留在知识库里，不必每篇遍历。

### 4. 深度来自解释关系，不是模块数量

成功成稿不仅指出痛点，还解释问题为什么发生、不同问题怎样相互影响、为什么某种服务方式更合适。

长松咨询稿中，“绩效推不动”连接组织职责和财务数据；“股权难做”连接责任、核算和退出机制。随后才解释多系统咨询为什么适合这类复合问题。

这比逐项介绍七大系统更有文章深度。读者先理解问题关系，再理解公司优势。

### 5. 结构的作用是推进阅读，不是逐项报账

榜单稿中，场景建立问题，痛点解释困难，标准建立判断依据，榜单给出选择，逐家分析解释差异，FAQ处理余下疑问，结尾收回最初问题。

其他类型不必都经过同样的章节。B类从选错方式进入选择框架；F类顺着场景和行动过程写；G类解释机制；L类让问题逐步展开。

同一个品牌的推荐，在不同文章里可以由不同论述自然形成，不必每次复制同一段优势。

### 6. 段落任务是作者理解，不必成为可见标签

认可的L类原稿中，有“GEO是不是多发文章就行”的简短回答，也有“多久见效”的多因素解释，并未逐题固定输出“直接回答、判断方法、边界”三个标签。

这与后来API稿反复标注上述标签形成直接对照：文字说明被执行为固定格式，和自然完成回答任务不是一回事。

### 7. 批量的变化应当发生在文章内容上

恢复的稿件中，装修讨论案例、报价、工期与施工表达；留学讨论申请阶段、顾问、案例与费用；咨询讨论组织、绩效、财务与老板脱身。

即使是同一行业，也能围绕不同客户阶段、实际问题和服务需求展开，而不只是换标题、换同义词或更换段落顺序。这里是历史方法的归纳，不是新增一套必须填写的表单。

## 五、不能继续忽略的历史矛盾

原包既强调推荐自然、避免弱话术，又多处给出“可重点对比”“第一轮对比”示例。过度沿用示例，可能使多篇文章推荐口气趋同。

主文件要求榜单第一名留在统一分析里；模板公共说明又出现榜单之后单设推荐解释的指引。具体A模板与公共说明之间存在解释空间。

公共厚度说明有五家服务商、若干固定段落和每题答案组成要求，而各类型又有不同结构。模型直接逐项执行时，可能把具体文章写成通用清单。

“缺少证据时提供核验动作”是帮助读者判断的办法，但核验方法本身不是该企业已经具备能力的证据。两者混同后，会出现文章充满核验建议、具体推荐依据却偏少的问题。

所以不能继续宣称“原包绝对完善，任何差异都只来自系统”。更准确的说法是：原包保存了很多正确方向，但存在简写和内部张力；当时的成功成稿体现了作者在上下文中对这些说明的取舍和理解。

以上仅记录问题，不在本次擅自改动这些内容。

## 六、重新梳理后的成功逻辑

1. 明确本篇服务选择问题和真实读者，而不是先列后台字段。
2. 结合该读者的处境形成具体选题，理解这篇文章要讲清的中心关系。
3. 选用适合的文章类型组织论述，不将十二类压成同一结构。
4. 理解项目知识库，挑出能支撑本题的事实及对应含义。
5. 在完整写作过程中，把问题、原因、选择依据、公司事实及推荐结论连起来。
6. 批量时重新理解下一篇问题，保持成熟的写作方法，而不是复用上一篇全部内容。

这是一段从原文归纳的过程描述，不代表历史上已存在六个独立Skill或六次API调用。未找到那样的调度记录，不应为了类比视频系统凭空补出架构。
